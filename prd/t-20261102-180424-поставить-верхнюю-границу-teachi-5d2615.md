# PRD — верхняя граница teaching-хода (turn fuse)

Источник: `.agent/review-2026-11-02.md` §3.3, `requests/t-20261102-180424-…md`.
Факты репозитория: `src/agent/teacher-agent.ts:153-155` (`maxTurns is gone`, owner ruling 2026-09-25);
`src/server/pi/ui-stream.ts:268-280` (единственный выход из внешнего цикла — `sawAbort`);
`src/agent/subagents/pi-run.ts:33` (у субагентов `maxTurns` есть); `src/agent/tool-execute.ts:46`
(`TOOL_TIMEOUT_MS = 30_000` — таймаут одного инструмента, а не хода).

## Goal

У application turn (prober / teacher / practice — один и тот же шов `baseAgentOptions` → `finishTurn` →
внешний `do/while` в `ui-stream.ts`) появляется предохранитель: по исчерпании предела ход
останавливается сам, с точным blocker, с записанным usage и без потери уже собранного транскрипта.

Предел — fuse, а не обычный лимит: на нормальном длинном уроке он не срабатывает. Owner ruling
2026-09-25 (снятие `maxTurns`) не отменяется: fuse не диктует модели, сколько ходов «правильно» делать,
он прекращает заведомо патологический цикл (повторяющаяся ошибка инструмента).

Размеры по умолчанию (из запроса, ориентир): **100 tool calls за ход**, **30 минут wall-clock**
на один application turn. Оба числа — константы модуля fuse, не env-настройки (см. Open questions).

## Non-goals

- Не возвращать `maxTurns` в teaching-агента и не менять его семантику.
- Не трогать субагентов (`src/agent/subagents/*`) — у них лимит уже есть.
- Не менять admission, liveness, 409-гвард, compaction, стрим-протокол, вопросный стоп-хук.
- Не вводить UI для настройки лимитов, не вводить новые env-переменные.
- Не вводить денежный бюджет как обязательный в этой задаче (см. Open questions, п.1).
- Не менять поведение инструментов, `TOOL_TIMEOUT_MS`, обработку ошибок провайдера.

## Use cases

1. Модель зациклилась на падающем инструменте. Turn доходит до 100-го tool call, fuse срабатывает,
   ран останавливается, в поток уходит `{type:"error"}` с blocker
   `turn fuse tripped: tool_calls=100 limit=100`, usage этого хода записан, частичный транскрипт сохранён.
2. Зависший провайдерский вызов: 30 минут от старта хода — таймер fuse вызывает `agent.abort()`,
   blocker `turn fuse tripped: wall_clock_ms=1800000 limit=1800000`, транскрипт сохраняется как при обычном abort.
3. Нормальный длинный урок (десятки квизов, ресерч, план) — 40 tool calls, 20 минут: fuse молчит,
   ход завершается как раньше, никакой ошибки в потоке нет.
4. Ученик нажал abort / задан вопрос — поведение не меняется: ход кончается вопросным стоп-хуком или abort'ом
   раньше, чем fuse успевает что-либо заметить.

## UX

Для учащегося fuse невидим, пока не сработал. При срабатывании:

- вместо обычного завершения приходит ошибка с blocker'ом (текст — как в `turn-fuse.ts`, английский,
  как остальные серверные тексты) и терминальный `turn-settled`;
- частичный ответ и выполнение инструментов, которые уже случились, остаются в транскрипте;
- следующий ход ученика работает штатно (никакого «сломанного чата»), как после abort.

Отдельного экрана, кнопки «продолжить» и ретрая нет.

## Edge cases

- Срабатывание ровно на пределе: 100-й tool call закрывает ход. 99 — не срабатывает.
- После срабатывания счётчик замирает на пределе; повторные наблюдения возвращают тот же trip
  (blocker не меняется, `observed` не растёт).
- `onFuseTrip` вызывается ровно один раз за ход (idempotent trip ≠ повторный отчёт).
- Вопросный ход (quiz / ask_user_question / problem) успел остановить ран на том же turn —
  trip не рапортуется (стоп-хук проверяется первым).
- Wall-clock таймер не держит процесс: `unref`, снимается на `agent_end`.
- Ход, завершившийся быстрее предела (в т.ч. abort ученика), не оставляет висящих таймеров.
- Usage отменённого/оборванного вызова не выдумывается: используется существующая фильтрация
  `usageWasAdmitted` / `stopReason === "aborted"` в `teacher-agent.ts`.
- Practice и prober получают fuse тем же швом; отдельных лимитов у них нет.

## Risks

- **Fuse стреляет на легальном уроке** — owner ruling 2026-09-25 был именно против лимита.
  Смягчение: пределы высокие (100 / 30 мин), тест «нормальный длинный урок проходит» в oracle,
  trip-событие видно в записи (blocker), а не молча.
- **Таймер в тестах оставляет открытые хендлы** — 30-минутный `setTimeout` обязан быть `unref`'нут
  и снят на `agent_end`; иначе `node --test` зависает.
- **Двойной отчёт** (trip из `finishTurn` и trip из таймера) — обязательный guard «один trip на ход».
- **Потеря usage при аварийном завершении**: если реализация оборвёт ран мимо штатного settlement,
  usage и частичные сообщения не запишутся. Требование: ход кончается штатным путём
  (`{action:"end"}` из `finishTurn` либо `agent.abort()`), а не исключением из середины.
- **Тихое расширение скоупа** в `chat-handler.ts` (admission, 409, compact) — запрещено спекой.

## Verification plan

1. `dod` (одна команда): oracle-тест `oracle/<ID>/turn-fuse.test.ts` через `node --test`.
   До реализации — падает (модуля `src/agent/turn-fuse.ts` нет), после — зелёный.
2. Oracle покрывает: политику fuse (предел 100 достигается ровно на 100-м вызове, 10k вызовов
   останавливаются на N, счётчик замирает, wall-clock срабатывает ровно на 30-й минуте и не раньше,
   override лимита параметром), trip через настоящий `createTeacherAgent` на scripted faux engine
   (одно срабатывание, точный blocker, ровно 100 tool calls в состоянии агента, usage собран),
   и отсутствие срабатывания на нормальном длинном уроке (40 вызовов).
3. Negative control: `oracle/negative/<ID>/kit.patch` — декалойный `src/agent/turn-fuse.ts`, который
   никогда не срабатывает; с ним oracle обязан упасть.
4. record-level запись usage (chat record, `appendTurnUsage`) отдельно не тестируется: канал
   `onUsage` → `appendTurnUsage` уже существует и спекой не меняется; oracle проверяет, что fuse
   не ломает сбор usage (коллектор получает события и при срабатывании).

## Open questions

1. **Денежный бюджет.** Для $ нужно знать цену модели на момент вызова (usage даёт токены, не деньги),
   а цены в записи хода не хранятся. Предложение: в этой задаче fuse считает tool calls + wall-clock;
   денежное измерение — отдельная задача после решения, откуда берётся pricing (таблица моделей vs поля usage).
2. **Пределы по умолчанию.** Запрос даёт ориентир 100 / 30 мин; спека фиксирует их как константы.
   Если owner хочет другие числа (например 200 / 60 мин) — это правка двух констант до старта работ.
3. **Переопределение через env** (`LH_TURN_FUSE_*`): предложено НЕ делать (нет запроса, лишняя
   конфигурационная поверхность). Если нужен — сказать сейчас, иначе константы.
