# PRD — Убрать потерю параллельных записей при компакции

## Goal

Компакция перестаёт затирать изменения записи, сделанные за время `await summarize`. Сейчас `compact()` (`src/server/compaction.ts:179`) читает снапшот `record.messages`, уходит в суммаризатор (строка ~229) и после ответа пишет `saveMessages(chatId, [...messages, marker])` (строка ~241) — полный массив из снапшота. `saveMessages` (`src/store/chats.ts:126-131`) заменяет `record.messages` целиком, без ревизии (`src/core/ports.ts:43-44`), поэтому всё, что параллельные писатели (`app/api/chats/[id]/artifact-ui/route.ts:39`, `app/api/chats/[id]/dismiss/route.ts:62`, settlement турна) добавили в окно ожидания, теряется.

Результат: конкурентная запись выживает компакцию; маркер компакции появляется ровно один раз и остаётся валидным (его `firstKeptMessageId` существует в итоговом массиве).

## Non-goals

- Не делаем межпроцессную/распределённую координацию: хранилище — один процесс, JSON-файл на чат.
- Не меняем формат `ChatRecord`, схему файла на диске и контракты `LhMessage`.
- Не переписываем admission/liveness (`beginTurn`, 409) и очередь компакции (`ensureCompacted` mutex).
- Не трогаем `app/api/chats/**` роуты, если выбранный механизм не требует их правки (см. Open questions).
- Не добавляем TLA-модель: риск medium, критерий задаётся тестом.

## Use cases

1. **Медленный суммаризатор + artifact toggle.** Тур идёт, порог контекста превышен, компакция стартует и ждёт суммаризатор. Пользователь переключает артефакт — роут пишет сообщение. Компакция завершается: toggle на месте, дивидер компакции на месте.
2. **Два dismiss параллельно с компакцией.** Два запроса dismiss пишут свои маркеры, пока компакция ждёт. Оба маркера и маркер компакции присутствуют; ни один dismiss не «съеден».
3. **Settlement во время компакции.** Тур завершается и дописывает native-сообщения, пока компакция ждёт. Итоговый массив = порядок «до cut» + новые сообщения + маркер компакции в правильной позиции.

## UX

Видимого изменения нет. Divider компакции появляется один раз, как и раньше; дублей маркеров нет; вместо молчаливой потери сообщения пользователь не видит ни ошибки, ни «прыжка» транскрипта. При конфликте записи — не тихое затирание, а наблюдаемая ошибка/повтор, ограниченный по числу попыток.

## Edge cases

- Пустой/пробельный summary → запись не меняется вообще (сохраняется текущее поведение `compaction.ts`).
- Чат удалён за время ожидания → записи нет, падения нет (`getChat` → null).
- Снапшот устарел так, что `cut` больше не описывает актуальный массив → маркер всё равно должен ссылаться на существующее сообщение (`firstKeptMessageId`), иначе `toLlmMessages`/`projectView` молча теряют хвост.
- Повторная/цепная компакция: `activeCompactionOf` должен видеть ровно один активный маркер, anti-churn guard не ломается.
- `appendTurnUsage` для маркера не должен задвоиться, если запись повторяется после конфликта (идемпотентность по `id` уже есть в store).
- Ошибка записи/конфликт после `await` → `compaction-changed {running:false}` всё равно эмитится (finally), запись остаётся честной.
- Порядок сообщений и `updatedAt`: конкурентная запись не должна откатывать `updatedAt` назад.

## Risks

- **CAS-маршрут** (`saveMessages(id, messages, expectedRevision)`): ревизию нужно протащить через всех писателей (`stores.ts`, роуты artifact-ui/dismiss, settlement, extraction-пути). Пропущенный писатель = постоянный конфликт/ошибка записи вместо тихой потери. Средний blast radius.
- **Actor-маршрут** (per-chat write queue, read-modify-write внутри актора): не требует правки вызовов, но добавляет очередь и риск дедлока, если писатель внутри актора сам ждёт другой актор/турн.
- Зависимость от p0-1 (атомарная запись): без неё даже корректный merge может дать рваный файл.
- Тест на реальных таймерах будет флакать: нужен детерминированный гейт (deferred/promise gate) вместо `setTimeout`.
- `npm test` гоняет весь набор `tests/*.test.ts`; критерий должен быть узким, иначе «dod» зависит от чужих падений.

## Verification plan

`dod`: `NODE_ENV=test npx tsx --test tests/compaction-concurrent-writes.test.ts` — на базе падает, после правки проходит.

Тест обязан покрыть (фейковый `ChatStore` в памяти + управляемый `summarize` через deferred):

1. компакция стартовала и ждёт суммаризатор → параллельный писатель добавляет сообщение `X` → суммаризатор отпущен → в записи есть `X` и ровно один маркер компакции, `firstKeptMessageId` указывает на существующее сообщение;
2. два конкурентных dismiss-подобных писателя во время компакции → оба сообщения и маркер компакции сохранены;
3. писатель, пришедший после завершения компакции, видит уже применённый маркер (нет отката к снапшоту);
4. пустой summary → запись не изменилась;
5. конфликт/исчерпание повторов (если выбран CAS) → явная ошибка, а не тихая потеря записи.

Negative control: `oracle/negative/<id>/kit.patch` — «near-miss» правка (перечитывает запись, но пишет по-прежнему снапшот). Oracle должен её отклонить.

## Open questions

- Механизм: per-chat write actor внутри store, или `saveMessages` с `expectedRevision` + CAS? Рекомендация — actor (read-modify-write под очередью на чат): закрывает всех писателей без протаскивания ревизии через роуты, минимальный diff в `compaction.ts` + `store/chats.ts`. CAS даёт явный контракт, но требует правки каждого вызова.
- p0-1 (атомарная запись) уже в `dev`? Если нет — эта задача не должна стартовать.
- Меняется ли публичная сигнатура `ChatStore.saveMessages` (ревизия в порту) или совместимость сохраняется и координация живёт в адаптере?
