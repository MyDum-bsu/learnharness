# PRD — закрыть файловым инструментам агента доступ к секретам и приватным данным

## Goal

Файловые инструменты агента (`read`, `ls`, `find`, `grep`) перестают отдавать в модельный контекст то, что не является учебным материалом: чужие секреты (`~/.ssh`, `~/.aws`, `.env*`), транскрипты других агентов (`~/.claude/projects/**`) и приватные данные самого приложения (`auth.json`, каталог `LH_DATA_DIR`, файлы credentials подписочных подключений, Electron `userData`). Проверка идёт по `realpath`, поэтому symlink из `~/notes` в `~/.ssh` правило не обходит. Совпавшие с секретом ключевые значения в выводе инструментов маскируются.

Текущее состояние (evidence из ревью): `src/agent/tools/fs-shared.ts:38` — `EXCLUDED_DIR_NAMES` содержит только `node_modules`, `.git`, `Library`, `.Trash`; `src/agent/tools/fs-shared.ts:43-47` — `resolveSourcePath` резолвит от home без deny-list; `src/agent/tools/read.ts:100-118` — `execute` читает файл без каких-либо проверок. Явные пути не фильтруются нигде.

Локальная ветка `pr-421` (upstream PR #421) закрывает только третьи стороны (`.claude`, `.ssh`, `.aws`, `.env`). Она берётся как база: в этой задаче к ней добавляется app-private deny-list, realpath-проверка и маскирование секретов в выводе.

## Non-goals

- Не делается sandbox/jail записи: инструменты остаются read-only, изменений в мутационные API нет.
- Не вводится пользовательский UI-настройки deny-list (никакого «разрешить всё» тумблера, никакого consent-диалога на чтение).
- Не меняется `EXCLUDED_DIR_NAMES` — шумовые исключения обхода (`node_modules`, `Library`, …) остаются шумовыми, запрет доступа живёт отдельным правилом.
- Не решается вопрос сетевой/провайдерной утечки уже прочитанного: если данные попали в контекст, задача их не отзывает.
- Не реализуется аутентификация сервера, LAN-защита и multi-user изоляция (это вне текущей модели доверия, см. `docs/development.md`).
- Не трогаются правила чтения внутри репозитория разработчика для собственных нужд (кроме случая, когда путь попадает в deny-list: `data/`, `auth.json` в корне репозитория).

## Use cases

1. **Ученик просит разобрать свои заметки.** `read ~/notes/lecture.md` работает как раньше; агент читает, видит содержимое, отвечает.
2. **Агент пытается «на всякий случай» прочитать `auth.json`.** Вызов отклоняется ошибкой инструмента с понятным текстом, файл не попадает в контекст, модель получает шанс исправить вызов.
3. **Агент идёт по home через `ls ~` / `find`.** Запрещённые каталоги не появляются в результатах обхода; явные пути внутри них отклоняются.
4. **Ревью разбора ключей.** Ученик просит посмотреть `.env.example`-подобный файл в своём проекте: т.к. `.env*` запрещён, инструмент отказывает явно. Чтение конфигурации без секретов делается через файл с другим именем (осознанное ограничение, см. Risks).
5. **Symlink.** В `~/notes/link-id` лежит symlink на `~/.ssh/id_rsa`; `read` отклоняет и его, потому что проверка идёт по разрешённому `realpath`.
6. **Секрет внутри легитимного файла.** Ученик читает `~/project/config.js` с живым ключом; текст читается, ключ в выводе инструмента заменён на `[redacted]`.

## UX

Пользовательских экранов задача не добавляет. Наблюдаемое поведение:

- **Отказ** — ошибка инструмента (не пустой результат), текст содержит `file access denied`, причину категории (например `credentials`, `app-private`, `agent-transcripts`) и сам путь в исходной записи модели. Модель видит ошибку и может перестроить вызов; UI показывает стандартный блок неуспешного tool result.
- **Обход** — запрещённые пути/каталоги просто отсутствуют в выдаче `ls`/`find`/`grep`; никаких «[skipped: denied]» строк в обычном выводе не добавляется.
- **Маскирование** — совпавшее значение заменяется ровно на `[redacted]`; имя ключа/путь остаются, чтобы ответ был осмысленным. Ограничения по объёму (50 KB, 2000 строк, `GREP_MAX_LINE_LENGTH`) считаются после маскирования.

## Edge cases

- Путь не существует, но лежит в запрещённом каталоге (`~/.ssh/id_rsa` на чистой машине) — отказ, а не ENOENT: проверка fail-closed по литеральному нормализованному пути, когда `realpath` невозможен.
- Symlink на запрещённый файл и symlink-каталог, внутри которого запрещённый файл.
- Symlink на разрешённый файл из `~/notes` — чтение разрешено (запрет по цели, не по факту symlink).
- Относительный путь и `~/` раскрываются как раньше (`resolveSourcePath`), затем проверяются.
- Путь с `..`, дублирующимися разделителями, trailing slash, не-нормализованный регистр (macOS case-insensitive): проверка после `path.resolve` + `realpath`.
- `LH_DATA_DIR`/`LH_AUTH_FILE` вне репозитория (дефолт `data/`, `auth.json` в корне) и внутри Electron `userData` в упакованном приложении.
- Запрещённый файл одновременно является целью `grep`-обхода: файл не открывается, содержимое не печатается, обход не падает.
- Бинарный файл в запрещённом каталоге: отказ до чтения (никакого `isBinaryFile` на запрещённом пути).
- Очень большой вывод с множеством совпадений: маскирование не должно раздувать вывод сверх `MAX_OUTPUT_BYTES` (проверять после маскирования).
- Значение, похожее на ключ, но безвредное (`sk-` внутри обычного слова, длинный hex-хэш в тексте заметок): маскирование не должно разрушать обычный учебный текст; ложноположительное срабатывание допустимо, потеря обычного текста — нет.

## Risks

| Риск | Что даёт | Чем платим | Что фиксирует потом |
|---|---|---|---|
| Deny-list по basename (`auth.json`, `*-credentials.json`) | закрывает app-private файлы независимо от того, где Electron положил `userData` | пользовательский `~/notes/auth.json` тоже перестанет читаться | если появится легитимный сценарий — сузить до известных корней отдельной задачей |
| Запрет всего `.env*` | простой и предсказуемый контракт (как в pr-421) | `.env.example`, `.env.template` тоже недоступны агенту | точечное исключение `.env.example` отдельным решением, если понадобится |
| Маскирование по эвристикам | ловит ключи, попавшие в легитимный файл | возможны ложные срабатывания на длинных токеноподобных строках | список паттернов расширяется в одном месте (`fs-deny.ts`) |
| Fail-closed на несуществующих путях | предсказуемость, нет `ENOENT`-утечки факта существования | сообщение об ошибке иногда «denied» вместо «not found» | — |
| Регрессия существующих тестов файловых инструментов | — | нужно править фикстуры, если они читают `.env`/`data/` | тесты остаются зелёными как часть DoD |

Риск medium, потому что меняется поведение всегда включённых инструментов и возможны ложные отказы на реальных файлах пользователя.

## Verification plan

1. `dod` (единственная команда спеки): `tsx --test` по oracle-файлу. Проверяет: отказ на `~/.ssh/id_rsa`, `~/.aws/credentials`, `.env*`, `~/.claude/projects/**`, `auth.json`, `dataDir/**`, credentials подписок; разрешение обычных заметок; отказ через symlink (файл и каталог); `defaultDenyScope()` следует `LH_DATA_DIR`/`LH_AUTH_FILE`; `redactSecrets` маскирует OpenAI/GitHub/AWS/Google/private-key/generic-password и не портит обычный текст и пути; `capOutput` маскирует; каждый модуль инструмента, объявляющий `read|ls|find|grep`, вызывает guard и маскирование.
2. `npm test` — существующий набор зелёный (в т.ч. тесты файловых инструментов), Node 26.
3. `npm run typecheck` — обязателен: добавляется новый модуль и меняются сигнатуры вызовов.
4. `npm run lint` — обязателен: ESLint-зоны `src/agent` (agents не импортируют server/store); новый модуль обязан остаться в `node:fs` и не тянуть Electron/Next.
5. Ручная приёмка по формулировке запроса: `read auth.json`, `read ~/.ssh/id_rsa`, `read .env` отклоняются; symlink из `~/notes` в `.ssh` отклоняется; key-like значение в выводе замаскировано.
6. Negative control: с `oracle/negative/<ID>/kit.patch` (заглушка guard'а, всегда «разрешено») `dod` обязан упасть.

## Open questions

1. Нужен ли исключённый из запрета `.env.example`/`.env.template`? Спека исходит из «нет»: `.env*` целиком, как в pr-421.
2. Должен ли отказ маскировать сам факт существования файла (отдавать `denied` и для несуществующего пути в запрещённом каталоге)? Спека исходит из «да» (fail-closed), чтобы не давать оракул существования.
3. Считать ли `~/.claude.json` (файл, не каталог) транскриптами агента? В спеку не входит; при желании добавляется одной строкой в deny-list.

Блок не блокирует работу: спека реализует указанные дефолты.
