# PRD: закрыть SSRF в `web_fetch` и `web_fetch_pdf`

## Goal

Агентские инструменты выхода в сеть (`web_fetch`, `web_fetch_pdf` в `src/agent/tools/web.ts`, `src/agent/tools/pdf-read.ts`) сейчас проверяют только схему URL (`src/agent/tools/web.ts:180-186`, `src/agent/tools/pdf-read.ts:105-132`) и следуют редиректам автоматически. Нужен единый сетевой гард: наружу уходит только `https` на публичный адрес, приватные/loopback/link-local диапазоны блокируются и по литералу, и по DNS-резолву, проверка повторяется на каждом хопе редиректа, DNS-резолв пиннится к тому адресу, который реально набирается, а Jina Reader не вызывается для адресов, не прошедших политику.

Инструмент остаётся non-throwing по контракту `web.ts`: отказ возвращается строкой ошибки, которую видит researcher, а не исключением в агентский цикл.

## Non-goals

- Не трогаем `web_search` и серверный поисковый адаптер (`src/server/search.ts`): он ходит к провайдеру по фиксированному хосту, а не по URL от модели.
- Не трогаем демо/визуальные инструменты и Electron browser helper: у них свой транспорт и своя модель доверия.
- Не меняем доставку брифов в user-канал (`src/agent/tools/jobs.ts:128-140`, `src/core/contracts/jobs.ts:350-353`) — это указание на ущерб от SSRF, а не место правки.
- Не вводим allowlist/override для dev (сценарий `http://127.0.0.1:3000/api/chats` — именно то, что должно быть закрыто) и не читаем env-переключателей.
- Не рефакторим экстракцию читаемого текста, лимиты размера и таймауты.

## Use cases

1. **Research-job пытается прочитать локальный API.** Исследователь вызывает `web_fetch("http://127.0.0.1:3000/api/chats")`. Отказ строкой, соединение не устанавливается.
2. **Редирект на loopback.** Разрешённый внешний URL отвечает `302 Location: https://127.0.0.1:3000/api/chats`. Второй хоп не набирается, инструмент возвращает отказ.
3. **Хостнейм, резолвящийся в loopback.** `web_fetch("https://localhost:3000/...")` или DNS-имя с A-записью `127.0.0.1` — отказ до соединения: валидация идёт по резолву, а не только по литералу.
4. **Внутренняя сеть и link-local.** `10.0.0.5`, `192.168.1.1`, `172.16.4.4`, `169.254.169.254` (metadata), `100.64.0.1` (CGNAT), `[::1]`, `[fe80::1]`, `[fc00::1]` — отказ.
5. **DNS rebinding.** Имя резолвится в приватный адрес между проверкой и соединением — гард блокирует на подключении, потому что проверенный адрес и есть набираемый.
6. **Внешний https работает.** Публичный `https` проходит политику и отдаёт контент как раньше (включая fallback на Jina для JS-страниц).

## UX

Агент видит строки вида `web_fetch failed for <url>: <причина>` / `web_fetch_pdf failed: <причина>`, где причина называет класс отказа: `blocked address (private/loopback/link-local)`, `only https is allowed`, `too many redirects`. Строка попадает в бриф researcher'а как есть; отдельного UI-элемента нет.

## Edge cases

- Литералы в нестандартной записи: `0x7f000001`, `2130706433`, `127.1`, `::ffff:127.0.0.1`, `[::ffff:7f00:1]`, trailing dot `localhost.`, uppercase host.
- Хост, не являющийся IP-литералом (обычное DNS-имя), который не резолвится: отказ с явной причиной, без падения.
- Цепочка редиректов длиннее лимита (5 хопов) — отказ, а не бесконечный цикл.
- Редирект с `https` на `http` или на нестандартный порт — отказ по схеме/политике на этом хопе.
- Редирект без `Location`, редирект на относительный путь, редирект-цикл.
- `web_fetch` получает PDF-URL на приватном адресе: отказ раньше, чем совет «вызови web_fetch_pdf».
- `web_fetch_pdf` на приватном адресе: файл не скачивается, временный файл не создаётся.

## Risks

- **Ломающее изменение:** внешний `http` (не `https`) больше не фетчится. Это прямое требование постановки, но затрагивает редкие сайты; отражено в отказе и в Open questions.
- **DPI/прокси:** проверка на уровне `lookup` может конфликтовать с корпоративными прокси; в этом репозитории прокси-путь не поддерживается.
- **Ложные срабатывания на публичных CDN с общими диапазонами** (например, `198.18.0.0/15` в некоторых тестовых сетях) — цена закрытия metadata- и loopback-доступа.
- **Обход через несоответствие транспорта:** если какой-то путь (Jina, PDF) останется на голом `fetch`, дыра вернётся. Поэтому гард один и подключается в оба инструмента.

## Verification plan

- Oracle-тест `oracle/<ID>/web-fetch-ssrf.test.ts` на `node:test` + `tsx`:
  - литеральный loopback и `https://localhost:PORT` через `web_fetch`/`web_fetch_pdf` → отказ, локальный сервер не получил ни одного запроса (счётчик `hits === 0`);
  - `http://` на внешний хост → отказ по схеме;
  - `isBlockedAddress` покрывает loopback/link-local/private/CGNAT/ULA/IPv4-mapped;
  - `guardedFetch` с инъецированным `lookup`, возвращающим `127.0.0.1`, отклоняет до вызова транспорта;
  - `guardedFetch` с фейковым транспортом, отдающим `302` на `https://127.0.0.1:3000/...`, отклоняет на втором хопе и вызывает транспорт ровно один раз;
  - `guardedFetch` с публичным `lookup` и фейковым `200` пропускает ответ (позитивный путь политики).
- `dod` — одна команда `NODE_ENV=test npx --no-install tsx --test oracle/<ID>/web-fetch-ssrf.test.ts`: до правки падает (гарда нет), после — зелёная.
- Негативный контроль `oracle/negative/<ID>/kit.patch`: наивная «починка» на базе (блокировка только литерала `127.`/`localhost` в первом хопе, без DNS и без проверки редиректов) — oracle обязан упасть на DNS- и redirect-кейсах.
- Реальный внешний `https` в автоматический `dod` не входит (сеть в гейте не гарантирована); он проверяется фейковым транспортом на уровне политики. Ручная/смоук-проверка внешнего https — за рамками гейта, отмечено как «not run» в отчёте воркера.

## Open questions

1. Блокировать внешний `http` полностью (формулировка «разрешать только внешние https») или разрешать `http` для публичных адресов, ограничившись блокировкой внутренних? План исходит из полного запрета `http`; если нужно иначе — правка одна, в `assertUrlPolicy`.
2. Нужен ли явный лимит хопов редиректа, отличный от 5? План фиксирует 5.
