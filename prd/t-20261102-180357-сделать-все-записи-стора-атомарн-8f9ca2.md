# PRD — t-20261102-180357-сделать-все-записи-стора-атомарн-8f9ca2

## Goal

Записи файлового стора в приложении перестают быть разрушаемыми падением процесса.
Каждая целая запись (`chats/<id>.json`, `settings.json`, `jobs/<id>.json`, JSON-карты
`graph/`, `auth.json`) идёт через один помощник: temp-файл в том же каталоге →
`fsync` файла → `rename` на цель → `fsync` каталога. Целевой файл никогда не бывает
пустым или обрезанным: читатель видит либо прошлое полное содержимое, либо новое полное.

Второе требование того же изменения: чтение битого JSON перестаёт быть тихим. Сейчас
`getChat` (`src/store/chats.ts:61-76`), `readSettings` (`src/store/settings.ts:39-43`) и
`getJob` (`src/store/jobs.ts:51-56`) ловят ошибку парсинга и возвращают `null`; из-за
этого испорченная сессия просто исчезает из списка, без следа в логе. Нужна явная ошибка
с путём к файлу и запись в `console.error`. `null` остаётся ровно за одним случаем —
файла нет.

Формат данных на диске не меняется: имена файлов, отступы JSON, поля, версии схемы и
фильтры чтения каталогов остаются как есть.

## Non-goals

- Не транзакции и не «exactly-once»: атомарна одна запись одного файла, не набор файлов.
- Ничего не меняется в JSONL-леджерах (`graph/{nodes,chains,sessions,coverage}.jsonl`,
  append-пути через `appendFileSync`) и в их формате.
- Не переписывается логика портов, схемы записей, `core/contracts.ts`, версии схем.
- Не вводится блокировок между процессами, WAL, журнал, ротация, восстановление стора.
- Не добавляются зависимости (`write-file-atomic` и подобные) — только `node:fs`.
- Не меняется UX сайдбара/ошибок в браузере, кроме следствия: битая сессия больше не
  «тихо исчезает», а даёт ошибку в логе сервера и пропускается списком с логом.
- Не трогаются другие P0 из плана 2026-11-02.

## Use cases

1. **Crash во время сохранения сессии.** Пользователь отправляет сообщение; сервер
   пишет `chats/<id>.json`; процесс убивают (SIGKILL / force quit / OOM). После
   перезапуска файл парсится, сессия на месте в сайдбаре, ссылка открывается.
   Сейчас в окне между `open('w')` (файл уже обрезан) и завершением `write` файл пустой.
2. **Force quit во время `settings.json`.** После перезапуска настройки — прежние
   валидные, а не «все заводские по умолчанию», как получилось бы из `null`.
3. **Прогресс фоновых задач.** `jobs/<id>.json` обновляется часто (строка прогресса);
   падение не должно оставлять пустой job-файл, из-за которого задача «потерялась».
4. **Битый файл лежит на диске** (старый баг, ручная правка, кончилось место). Чтение
   даёт ошибку `chat <id>: corrupt record at <path>: <cause>` в лог и вызывающему коду;
   список сессий продолжает работать, битая запись пропускается с логом.
5. **Разработчик/агент меняет стор.** Любая новая запись в `src/store/` обязана идти
   через помощник — прямой `fs.writeFileSync` по цели ловится тестом.

## UX

Внешнего UI-изменения нет. Наблюдаемые следствия:

- После падения во время сохранения сессия доступна: список, ссылка, история вплоть
  до последнего завершённого сохранения.
- Для битого файла: серверный лог содержит одну строку с путём и причиной; сайдбар
  не пустеет, остальные сессии видны. Запрос одной битой сессии отвечает ошибкой
  (существующий обработчик роута), а не 404 «нет такой».
- Для отсутствующего файла поведение прежнее (первый запуск, `null`).

Деградация, которую принимаем сознательно: если `settings.json` испорчен, приложение
не подставляет заводские значения молча, а падает с явной ошибкой при первом чтении.
Это требование постановки («явная ошибка, а не тихий null»); восстановление — удаление
или починка файла, это описано в `docs/architecture.md` §8.

## Edge cases

- Падение между `write(temp)` и `rename` — целевой файл не тронут; в каталоге остаётся
  `*.json.tmp`. Temp не оканчивается на `.json`, поэтому фильтры чтения каталога
  (`filter(f => f.endsWith(".json"))`) его не видят.
- Падение между `rename` и `fsync(dir)` — содержимое уже целое; потеря устойчивости
  к потере питания, не к падению процесса.
- Падение при создании файла впервые (цели ещё нет) — либо цели нет, либо файл целый.
- Каталог отсутствует — `mkdirSync(recursive)` до записи temp.
- Цель — симлинк/чужой inode: `rename` заменяет запись, а не цель симлинка. Не чиним,
  поведение фиксируется тестом как есть (файлы стора не симлинки).
- Уже испорченный файл от старого бага: чтение бросает ошибку, стор **не** перезаписывает
  его автоматически (никакого «самовосстановления» из пустого файла).
- Пустой файл (0 байт) — тоже битый, не «пустая запись»: ошибка с путём.
- Два `saveMessages` подряд в одном процессе — read-modify-write не прерывается
  (синхронный код), атомарность нужна против падения, не против гонки; межпроцессная
  гонка остаётся вне скоупа (один владелец профиля данных).
- Windows/APFS/ext4: `fs.renameSync` поверх существующего файла заменяет цель.
- Стоимость: `fsync` на каждый persist сессии и на каждую строку прогресса job. Прирост
  латентности на turn-persist принимаем; если он окажется заметным, это отдельная задача.

## Risks

- **Риск блокирующего поведения на boot-пути.** `readSettings` теперь бросает на битом
  файле; вызывающие места должны пробрасывать ошибку, а не превращать её в дефолты
  (иначе требование выполнено формально и тихо). Проверяется oracle-тестом на битом
  `settings.json`.
- **Риск частичного скоупа.** Постановка перечисляет пять видов записей; `auth.json`
  может писаться вне `src/store/` (Electron main / `LH_AUTH_FILE`). Если так — это
  отдельный вопрос (см. Open questions), а не повод расширять диф.
- **Риск подмены критерия.** Самый дешёвый «зелёный» путь — temp+rename без `fsync` и
  без изменения чтения. На это есть negative corpus: он должен быть отвергнут на тесте
  явной ошибки чтения.
- **Риск oracle-фикстуры.** Crash-тест гоняет реальный порт `chats`; он опирается на
  существующие сигнатуры `createChat(id-генерирующий)`, `getChat(id)` и
  `saveMessages(...)` и на то, что адаптер пишет переданные сообщения как есть. Если
  порт отвергает форму сообщения из фикстуры — это дефект фикстуры, его нельзя «чинить»
  правкой oracle.
- **Риск inode-проверки.** Тест «запись заменяет файл» опирается на смену inode; на ФС
  без стабильных inode он ложно упадёт. Окружение CI — обычная локальная ФС.

## Verification plan

1. `dod` (одна команда, падает до, проходит после): oracle-набор
   `.factory/integration/oracle/<ID>/store-atomic.test.ts`. Внутри четыре критерия:
   - SIGKILL во время сохранения чата в цикле (по seed, N прогонов): после каждого
     убийства `chats/<id>.json` парсится, число сообщений кратно размеру прохода,
     то есть запись завершена целиком;
   - каждая запись (chats / settings / jobs) заменяет файл (inode меняется) вместо
     обрезки на месте;
   - битый JSON в chats / settings / jobs даёт ошибку с путём к файлу, `listChats`
     пропускает запись с записью в `console.error`;
   - прямой `fs.writeFileSync` встречается ровно в одном модуле `src/store/`.
2. Регрессия поведения: `npm test` (все существующие наборы), отдельно
   `tests/golden-fixtures.test.ts` — формат golden-данных не изменился.
3. Контракты затронуты (персистентность): `npm run typecheck` и `npm run lint`
   (в частности ограничения импортов из `eslint.config.mjs`).
4. Ручная проверка симптома: заполнить `data/chats/<id>.json` мусором, прочитать сессию —
   в логе строка с путём, сайдбар остаётся живым.

Все прогоны — на Node 26 (как требует постановка).

## Open questions

- `auth.json` (`LH_AUTH_FILE`): постановка включает его в список «все записи стора», но
  писатель может находиться вне `src/store/` (например, в Electron main). Если писатель
  вне `src/store/`, воркер сообщает это как блокер и не расширяет `allowed_paths`
  самостоятельно. Решение о расширении скоупа — за владельцем.
