# Spec — атомарные записи стора

## Intent

Убрать разрушаемость файлового стора падением процесса и убрать тихое проглатывание
ошибок чтения. Каждая запись целого JSON-файла стора идёт через один помощник:
temp в том же каталоге → `fsync` файла → `rename` на цель → `fsync` каталога. Битый
файл при чтении даёт ошибку с путём к файлу и строку в `console.error`; `null`
остаётся только за «файла нет».

Область: `src/store/chats.ts`, `src/store/settings.ts`, `src/store/jobs.ts`, JSON-карты
`src/store/graph.ts`, и писатель `auth.json` — если он находится под `src/store/`.
Формат данных и сигнатуры портов не меняются. JSONL-леджеры (`appendFileSync`) не
переводятся на перезапись.

## Given

- `writeChat` (`src/store/chats.ts:57-59`) пишет `fs.writeFileSync` прямо в цель:
  файл сначала обрезан, потом заполняется.
- `writeSettings` (`src/store/settings.ts:57`) и записи job (`src/store/jobs.ts:45,65`)
  делают то же.
- Читатели глотают ошибку парсинга: `getChat` (`src/store/chats.ts:61-76`) → `null`,
  `readSettings` (`src/store/settings.ts:39-43`) → `null` («заводские значения»),
  `getJob` (`src/store/jobs.ts:51-56`) → `null`.
- Испытательный стенд: `tsx --test`, тесты кладут данные через `LH_DATA_DIR`
  (`npm test`, `docs/architecture.md` §8, §10).

## When

- Процесс убивают (SIGKILL / force quit) в момент, когда идёт сохранение сессии,
  настроек или job-файла.
- Или: на диске лежит битый/пустой JSON-файл стора, и его читают.

## Then

1. После SIGKILL во время сохранения `chats/<id>.json` парсится, а число сообщений
   соответствует целиком завершённому сохранению; сессия видна в `listChats` и читается
   `getChat`. То же по смыслу для `settings.json` и `jobs/<id>.json`.
2. Запись заменяет файл (inode меняется), а не обрезает и переписывает его на месте —
   для чатов, настроек и job-файлов.
3. Чтение битого `chats/<id>.json`, `settings.json`, `jobs/<id>.json` бросает `Error`,
   в тексте которого есть имя файла; `listChats` не пустеет, битую запись пропускает и
   пишет строку в `console.error` с её именем.
4. Файла нет → по-прежнему `null` (первый запуск), без ошибки.
5. Во всём `src/store/` прямой `fs.writeFileSync` встречается ровно в одном модуле —
   помощнике; остальные зовут его.
6. `npm test`, `npm run typecheck`, `npm run lint` зелёные; golden-фикстуры
   (`tests/fixtures/golden-data/`) не менялись.
7. `dod` проходит, все `properties.seeds` проходят.

## Forbidden

- Менять формат на диске: имена, отступы, поля, версии схемы, `graph/format.json`.
- Менять публичные сигнатуры `ChatStore`/`SettingsStore`/`JobStore`/`GraphStore`
  и типы в `src/core/contracts.ts`.
- Трогать JSONL-леджеры и append-пути (`appendFileSync`) — они вне скоупа.
- Оставлять `catch { return null }` на пути парсинга: `null` только для `ENOENT`.
- «Самовосстановление»: перезапись битого файла дефолтами или пустой записью при чтении.
- Добавлять зависимости и трогать `package.json` (`gate_inputs`).
- Скрытые ретраи, `try/catch` вокруг `rename`/`fsync` с проглатыванием ошибки, `TODO`
  и заглушки вместо реализации.
- Temp-файл с суффиксом `.json` (он попадёт в чтение каталога) или в другом каталоге
  (rename через границу ФС не атомарен).
- Правка `oracle/`, `prd/`, `specs/`, `requests/`; расширение `allowed_paths`
  самостоятельно — при нехватке скоупа (например `auth.json` вне `src/store/`) воркер
  останавливается и сообщает блокер.
- Любые изменения вне персистентности: sidebar, роуты, промпты, UI-ошибки — только
  следствия, вытекающие из п.3.
